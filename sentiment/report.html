xev-sentiment 实验报告

我们从 Qwen3.5-4B-Base 开始，用自己写的 LoRA + Kev-style pointer head 代码，在清洗后的 ChnSentiCorp 上做了 2 个 epoch 的 post-training，得到一个输出 calibrated probability 的中文 sentiment classifier。在领域内的 test 上，它比不训练的 zero-shot baseline 准确率高 5.2 个百分点；但在没见过的外卖评论上，它反而比 baseline 低 1.3 个百分点。

Test accuracy（848 条）0.956比 baseline 0.905 高 +5.2 pp，CI [+3.5, +7.0]
Test NLL0.123baseline 0.236，约减半
错误率 ≤1% 时可自动处理85.7%baseline 42.7%
外卖 OOD accuracy（11,973 条）0.886比 baseline 0.899 低 −1.3 pp，CI [−1.8, −0.9]

主要发现

  1. 原始 ChnSentiCorp 切分有严重 leakage。test 里 324 条（27%）、validation 里 328 条和 train 一字不差，另有 36 条评论在不同副本里标签互相矛盾。全部删除后，test 剩 848 条。
  2. Zero-shot baseline 已经很强。不训练的 Qwen3.5-4B-Base 读 A/B 字母概率，validation 上就有 0.892 的准确率、0.031 的 ECE。
  3. Post-training 在领域内明显有效，校准也更好。test accuracy 0.905 → 0.956；NLL、Brier 都约减半；交换选项顺序答案改变的比例 2.0% → 0.35%。
  4. 但领域外略变差。外卖评论很短（47% 不超过 10 个 token），正面只占 33%；模型在长评论、正面占 53% 的数据上训练后，对这种分布不如 base model 稳。
  5. 剩下的错误里有不少是标注错误。最有把握的 15 个 test 错误中，约 10 个看起来是标签标反了。

2

数据清洗：原始切分有严重 leakage

数据是 lansinuote/ChnSentiCorp @ b0c4c119（酒店、笔记本电脑、书籍三个领域的中文评论）。清洗按顺序做三件事：删掉标签互相矛盾的评论（同一段文字在不同地方被标成相反的标签，所有副本都删）；同一个 split 里的重复只保留一条；validation 和 test 里与 train 一字不差的评论全部删掉。

split原始标签矛盾重复与 train 重复保留negativepositivetoken p50 / p99
  • test 里 324 条（27%）和 train 完全一样。用原始切分训练再测，等于有四分之一以上的题是模型背过答案的，公开的 ChnSentiCorp 准确率因此可能偏高；我们的数字因为去掉了这些题，会比公开数字低，但更可信。
  • 长度：token p99 约 320，截断长度 384 覆盖 99% 以上的评论。
  • 清洗后正面比例：train 53%，test 59%，略有不同，所以同时报告两类各自的 recall。

Zero-shot baseline

保留 base model 的 LM head，用 prompt 评论：…\n这条评论的情感是？\nA. 正面\nB. 负面\n答案：，比较下一个 token 是 "A" 还是 "B" 的 logit。两种选项顺序各跑一遍再平均，消除对字母位置的偏好。温度在 validation 上拟合（T=1.20），test 和外卖数据直接沿用。

这个 baseline 不弱：不用任何训练，准确率接近 90%，概率也基本是准的。这说明 4B 的 base model 本身已经"懂"情感，post-training 要做的是把这份能力读得更准。

4

训练过程

Smoke run 发现：head 的 learning rate 太大

第一次 smoke run（20 步）里，loss 在前几步冲到了 45，而两个选项的随机猜测只应是 ln 2 ≈ 0.69。测量发现：初始化时 loss 只有 1.14，问题不在初始化；backbone 输出的 hidden state 范数约 160，pointer head 用 1e-3 的 lr 时，一次 AdamW 更新就让 2,560 维上每个权重都动 1e-3 左右，累加起来把分数推到极端。我们把 W_k 改为零初始化（初始 loss 正好 0.693），再对比两种 head lr：

Head lr 1e-3 时 loss 仍会冲高，1e-4 从头到尾平稳

两次 smoke run，320 条样本、20 步、5 步 warmup，W_k 都零初始化。纵轴是对数刻度。

完整训练

完整训练用时 36 分钟，显存峰值 10.2 GB，约 740 tokens/s。train loss 从 0.48 降到 0.08。下图是 train loss（每 20 步）和 validation NLL（每 200 步）：

Validation NLL 在 step 1000 最低，accuracy 最高的 step 800 反而 NLL 偏高

Test 结果（领域内，只读一次）

所有设置在 test 打开之前都已固定。Baseline 与我们的模型在同一批 848 条上比较，accuracy 差用 paired bootstrap（1,000 次）给出 95% 区间。

modelaccuracyNLLECEBrier≥0.9 却答错coverage@1%order flip
Zero-shot baseline（T=1.20）0.9050.2360.0240.1402.2%42.7%2.0%
Ours（T=1）0.9560.1270.0210.0712.4%85.7%0.35%
Ours（T=1.23）0.9560.1230.0160.0691.7%85.7%0.35%

领域内明显变好，领域外略变差

点是 accuracy，横线是我们的模型相对 baseline 的差及其 95% 区间（paired bootstrap），右侧标注。

  • Recall：negative 0.934 → 0.977，positive 0.885 → 0.942，两类都提高。
  • Coverage@1%：按把握从高到低只自动处理一部分评论，要求错误率不超过 1% 时，最多能处理 85.7%（baseline 42.7%）。错误率要求放宽到 5% 时，我们的模型可以全部自动处理，因为总错误率只有 4.4%。
  • Order flip：训练时随机交换选项顺序起了作用，交换后答案改变的比例从 2.0% 降到 0.35%。
  • 互补性：848 条里，只有我们答对的 48 条，只有 baseline 答对的 4 条。

三个领域都提高，酒店评论最难

每行两个点：灰色 baseline，紫色 ours；连线绿色表示提高，红色表示下降。按关键词粗分领域（"mixed"同时提到几个领域，"unclear"分不出来）。括号里是评论数。

Calibration 能迁移到 test：说 98% 把握的评论，实际 99% 答对

Reliability diagram：横轴是平均把握，纵轴是实际准确率，点的大小表示评论数，对角线是完美校准。左边是 ChnSentiCorp test，右边是外卖 OOD；都用 T=1.23。把握低于 0.85 的桶评论很少，波动大。

Out-of-domain：外卖评论

数据是 XiangPan/waimai_10k @ dbb12540 的原始 CSV（Hub 上的 parquet 副本是乱码，没用）。同样删掉标签矛盾的 14 行，剩 11,973 条：negative 7,980，positive 3,993。与 ChnSentiCorp train 没有重复。两个模型都沿用 ChnSentiCorp validation 上定好的 T，外卖数据上没有重新拟合任何东西。

modelaccuracyNLLECE≥0.9 却答错coverage@5%recall neg / posorder flip
Zero-shot baseline（T=1.20）0.8990.2680.0072.9%79.2%0.929 / 0.8412.6%
Ours（T=1）0.8860.3270.0485.5%67.5%0.890 / 0.8790.9%
Ours（T=1.23）0.8860.3080.0234.0%67.5%0.890 / 0.879
结论：在外卖评论上，我们的模型 accuracy 比 baseline 低 1.3 个百分点（95% CI [−1.8, −0.9]，不含 0），校准也更差（ECE 0.023 vs 0.007）。只在一个领域上训练，让模型更专门化，换到新领域时不如 base model 稳。

为什么会变差

外卖评论很短，短评论上我们的模型不如 baseline

按 token 长度分桶的 accuracy，每行两个点：灰色 baseline，紫色 ours；连线红色表示我们的模型更差。外卖数据有 47% 不超过 10 个 token，而 ChnSentiCorp test 里这样短的只有 3 条（图中省略）。超过 100 个 token 的外卖评论只有 58 条。

  • 长度分布不同：ChnSentiCorp 评论 token 中位数 46，外卖只有 11。模型几乎没见过"送餐很快"这种一句话的评论。在 31–100 token 的外卖评论上，差距也存在（0.937 vs 0.957），所以长度不是唯一原因。
  • 正负比例不同：外卖只有 33% 是正面，训练集是 53%。我们的模型在外卖上预测正面 36.7%，baseline 32.8%，更接近真实的 33.4%。negative recall 从 0.929 掉到 0.890，正是多判了正面造成的。
  • 领域词汇不同："送餐""配送费""分量"这类外卖特有的说法，训练数据里基本没有。
  • 外卖数据本身也有噪声：两个模型都以 ≥90% 的把握否定标签的评论有 244 条（2.0%），例如"配送费越来越贵！！！！"被标成 positive。去掉这些后两者是 0.904 vs 0.918，差距依旧。

错误分析

Test 上一共 37 个错误。按模型把握从高到低排，最前面的大多是标签标反了，少数是反讽和褒贬混合。两个模型都以 ≥90% 的把握否定标签的 test 评论有 8 条（0.9%）；去掉它们，我们的模型 accuracy 是 0.965，baseline 0.913。

结论与下一步

  • 领域内：36 分钟、33.8M 个可训练参数的 LoRA + pointer head post-training，把 test accuracy 从 0.905 提到 0.956，NLL 减半，可在 1% 错误率内自动处理的比例翻倍。这是本次实验最主要的结果。
  • 领域外：同一个模型在外卖评论上比 base model 差 1.3 个百分点，校准也变差。如果实际要处理的评论和训练数据不一样，直接用 base model 的 zero-shot 读法可能更稳。
  • 数据：原始 ChnSentiCorp 切分的 leakage 和标签噪声都很明显，用它报告的准确率需要谨慎解读。

局限

  • 只跑了一个 seed，没有做 hyperparameter search；结果的波动范围只能从 bootstrap 区间粗略估计。
  • 领域划分和"标签错误"的判断都是关键词和人工阅读，不严格。
  • 外卖评论只用来测，没有用来调任何设置，这是有意的；但也因此不知道少量外卖数据能弥补多少差距。

下一步可以试

  1. 混入短评论和其他领域的数据（例如一小部分外卖或微博评论）一起训练，再看领域外的表现。
  2. 减少对 base model 的改动：只训练 1 个 epoch、更小的 LoRA rank，或用 KL 约束让输出别离 base model 的 zero-shot 分布太远，看能否保住领域外的能力。
  3. 清洗标签：把两个模型都高置信否定标签的样本拿出来人工复核，重新评估。
  4. 多跑几个 seed，确认 +5.2 和 −1.3 这两个差距的稳定性。

复现

代码在 G:\dev\repo\xev\sentiment，在 WSL 里先 source env.sh：

uv sync
uv run python prepare_data.py                     # Step 1
uv run python baseline.py --split validation      # Step 2
uv run python train.py --out runs/main            # Step 4（36 分钟）
uv run python calibrate.py --run runs/main        # Step 5
uv run python baseline.py --split test --temperature 1.2030
uv run python evaluate.py --run runs/main         # Step 6
uv run python prepare_ood.py && uv run python baseline.py --split waimai --temperature 1.2030 \
  && uv run python evaluate.py --run runs/main --split waimai
uv run python tools/analyze.py
uv run uvicorn serve:app --port 8010              # Step 7

结果文件：runs/main/{eval_test,eval_waimai,calibration,analysis,summary}.json、runs/main/train_log.jsonl、runs/baseline/*.json。
